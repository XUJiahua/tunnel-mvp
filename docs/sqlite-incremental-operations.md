# SQLite 增量持久化操作

本批无需手动迁移，SQLite schema/backup 仍为 v10。按既有流程停机、导出授权备份与运维归档后替换程序，重新启动；内存差异缓存会由现有数据库构建，不能复制其他进程的缓存或直接在线改库。

领域校验、FULL 同步、事务和目录锁保持启用；遇到保存失败，API 返回失败，内存与磁盘仍为上次提交。检查磁盘空间、权限和 SQLite 错误后重试，不应删除数据库或关闭外键来绕过。备份/restore/迁移仍在离线目录锁下执行，恢复后缓存重新初始化。

## 稀疏更新基准

同一 Linux / Go 1.27.2，1001 用户、1000 条整站 grant、1 站点、1 应用；每轮 20 次单站点改名，连续三轮。基线为 PR #15 的完整重写实现，复制同一 `sqlite_delta_benchmark_test.go` 到基线工作树；新实现使用本批代码。时间包含快照/领域验证/差异/提交，初始化不计入。

| 实现 | 每次受影响 SQL 行 | 时间 ms/op（三轮） | B/op（三轮） | allocs/op（三轮） |
| --- | ---: | --- | --- | --- |
| 完整重写 | 4006 | 31.70 / 29.85 / 34.97 | 3,950,970 / 3,912,891 / 3,875,432 | 33,768 / 33,762 / 33,784 |
| 增量 | 2 | 10.87 / 13.93 / 10.94 | 4,095,760 / 4,029,665 / 4,265,357 | 15,061 / 15,061 / 15,067 |

SQL 行减少 2003 倍；这组本地计时约快 2–3 倍，内存字节分配略高，不能把它解释为生产吞吐或数据库 HA 能力。整体验证/快照仍然线性，位置重排和大规模授权修改仍可能触及很多行。

```sh
go test ./internal/state -run '^$' -bench BenchmarkSQLiteSparseRename \
  -benchtime=20x -count=3 -benchmem
```
