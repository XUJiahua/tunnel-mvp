# 多管理员与管理变更排序

第六层依赖用户组与邀请批次，支持多个独立的全局管理员。每位管理员拥有独立凭据、设备和审计身份，避免共享 bootstrap 账号。组织管理员、自定义角色在后续层实现，本层 admin 仍为全局权限。

## 操作与凭据

| API | 行为 |
| --- | --- |
| `POST /api/administrators` | 当前管理员密码、用户名和初始密码，创建全局管理员 |
| `PATCH /api/administrators/{id}` | 当前密码与 action：promote/demote/disable/enable |
| `DELETE /api/administrators/{id}` | 当前密码，删除管理员 |

以上均要求当前管理员会话、exact Origin、JSON 严格字段和每分钟全局 20 次上限。每次重新比较当前持久化 bcrypt hash，不缓存再次验证结果；OIDC 登录的管理员仍需本地恢复密码完成此类操作。新账号密码 12–72 字节。邀请不创建管理员，OIDC-only/停用成员不能被提升。管理员不能重置另一位管理员密码；各自使用改密或离线恢复。

提升、降权、启用、停用、删除均撤销目标账号全部控制台会话、应用 Cookie 与短期票据，并取消其 HTTP/WS/SSE。提升不能让旧会话静默获得管理员权限。降权保留原先直接和组授权，并不转化管理员的全局访问为持久化整站授权。创建不撤销发起者会话。

状态验证始终要求至少一个启用且有本地密码的 admin。禁用/删除/降权最后一个此类账号会回滚，即使两个管理员并发停用自己，也只有一个能成功。可对自己执行操作，但需要另一个恢复管理员；成功后自己立即重新登录。删除同时清理组成员引用。

## 并发边界

管理写入从鉴权到持久化、撤销在同一 accessMu 写锁内完成，涵盖原先创建站点、应用、成员等未再次验证会话的入口。先完成的撤销使后来取得锁的旧会话失败；已提交的合法写入先于后来的撤销。上下文私有标记让已有 handler 的锁可复用，不递归锁；成员/公共端点仍自行加锁。网络代理只在注册与鉴权时持锁，不持锁转发网络流量。

不增加数据库 schema；复用现有 admin/viewer 及 Disabled。JSON/SQLite 验证同样执行最后恢复账号约束。

## 验证

API/race 测试覆盖成员越权、错误密码、创建、提升后旧会话失效、启停/降权/删除、最后管理员三种破坏操作拒绝，以及两个管理员并发自停用。浏览器通过真实 Agent 打开应用，再降权撤销旧设备和应用访问，复验提升/删除和手机布局。双后端执行完整回归，避免统一管理锁破坏 OIDC、组授权和设备撤销。

发布工具 v2.18.3 在本环境串行模式仍出现 gzip 尾部缺失；标准 Go gzip 独立复现 12 个包全部正常，根因尚未证明。固定已验证的 v2.17.1，检查实际版本，并保留六平台全流解压/CRC/内容/SHA-256；不是忽略失败或修改旧包补尾部。
