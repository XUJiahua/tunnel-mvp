# 状态存储、SQLite 与迁移设计

本批在 `feat/operations-and-access` 上继续开发，作为依赖 PR #1 的 stacked PR。仅包含存储与离线维护增量，不合并前一批，也不修改 `main`。

## 1. 决策

默认继续使用 JSON，新增 `storage: sqlite` 选项。SQLite 用于单机部署中的事务、约束与版本管理，控制面仍是一个进程。会话、短期票据、探测结果和 Agent 隧道归属仍在内存中，因此不声称支持 HA。

驱动固定为 `modernc.org/sqlite v1.60.1`，保持 `CGO_ENABLED=0`；进程锁固定使用 `github.com/gofrs/flock v0.12.1`。驱动和锁的跨平台编译加入现有 Linux/macOS/Windows × amd64/arm64 六平台 CI。

参考：[SQLite 驱动文档](https://pkg.go.dev/modernc.org/sqlite@v1.60.1)、[flock](https://github.com/gofrs/flock/tree/v0.12.1)。选择单机数据库与后续选择共享数据库是两项不同决策。

## 2. Repository 边界

`internal/state` 拥有用户、站点、应用和授权模型，暴露：

```go
type Repository interface {
    Snapshot() State
    Update(func(*State) error) error
    Close() error
}
```

控制面保留薄适配器和原有查找方法；鉴权、隧道和 HTTP handler 不依赖 SQLite SQL。后续身份提供方也应通过该接口持久化，不直接修改数据库文件。

读模型保存在内存中，Snapshot 返回深拷贝。Update 在互斥锁内复制当前状态、执行回调、验证完整状态、提交持久化，最后替换缓存。回调拒绝、校验失败或持久化失败时，缓存保持原值。提交后再次复制，避免回调保留的切片引用修改已提交状态。

本版 SQLite 每次在一个事务中重写配置聚合，复杂度仍与配置总量相关；它补齐事务和结构约束，不是大规模增量 SQL 查询优化。后续可在 Repository 后调整增量写入策略。

## 3. 进程与文件生命周期

Server 和所有读取活动数据目录的离线命令，都持有该目录的独占文件锁。锁覆盖读入、整个运行周期或维护操作。第二个 Server、迁移、导出或检查命令立即报 `data directory is in use`，不等待、不删除锁文件。

锁由操作系统管理，进程退出后释放；`.tunnel.lock` 文件保留，防止删除后两个进程分别锁住不同 inode。它是遵守协议的进程之间的保护，不阻止用户用其他程序手改文件，也不能保护仍运行的旧版 Server。使用本地磁盘，不支持多主机共享目录或把锁当分布式锁。

打开已有数据失败时绝不重新初始化管理员。启动在审计文件或其他后续步骤失败时也会关闭存储并释放锁。关闭存储是幂等操作，先关闭数据库再释放目录锁。

## 4. SQLite schema v1

数据库为 `state.db`，设置固定 `application_id = 0x54554e4c`（TUNL）与 `user_version = 1`。打开已有数据库时验证标识、版本、quick_check、外键与业务模型。未知版本、错误文件、缺表或损坏数据均拒绝启动，不自动降级或覆盖。

| 表 | 内容与关键约束 |
| --- | --- |
| `users` | ID 主键、用户名唯一、密码散列、admin/viewer 角色 |
| `sites` | ID 主键、名称、SHA-256 令牌散列、创建时间 |
| `services` | ID 主键、所属站点外键、名称和 HTTP/HTTPS 源地址 |
| `user_sites` | 用户/站点外键，授权组合唯一 |
| `user_services` | 用户/应用外键，授权组合唯一 |

主表和授权表记录 position，保证迁移/恢复后保持列表顺序。业务层另外检查 ID、名称、角色、bcrypt 格式、令牌散列、至少一个管理员、目标 URL 和所有引用；空授权列表标准化为空数组，重复授权去重。

数据库使用单连接、外键开启、5 秒 busy timeout、FULL synchronous 和 DELETE journal。配置读使用内存快照，不需要 WAL 读写并发。事务失败会完整回滚，包括此前已删除/重写的记录。不要用外部程序改变 journal 模式或直接编辑表。

未来 schema 升级应提供显式、受测试的版本迁移。目前只有 v1，不把任意零版本数据库当成可初始化的空库。

## 5. 创建与原子发布

首次初始化、JSON → SQLite 迁移和备份恢复，先在同一目录生成权限 0600 的临时文件。完整写入、校验、提交、关闭 SQLite 并同步文件后，用硬链接原子发布最终文件名；目标已存在时拒绝，不覆盖、不提供 force 参数。临时文件随后清理。

这一选择避免“检查目标不存在，然后 rename 覆盖了并发创建的文件”的窗口。要求本地文件系统支持同目录硬链接；不支持时命令失败并保留原数据，不采用不安全的覆盖回退。进程异常退出可能留下临时文件，应停机确认后处理，不能当作成功迁移。

JSON 正常更新沿用临时文件写入/fsync/原子替换。新建目录默认 0700，新状态和备份文件默认 0600；已有目录权限由部署者负责。

发现 `state.db` 时，即使 `state.json` 还存在，JSON 模式也拒绝启动，避免迁移后悄悄读写过期的 JSON。SQLite 模式在仅有 JSON、尚无数据库时要求先迁移，避免初始化一个空数据库。数据库缺失但存在 journal/WAL/SHM 残留时拒绝初始化或恢复，交由操作者先确认恢复状态。

## 6. 迁移

`storage migrate --from json --to sqlite`：

1. 获取已有目录的独占锁，拒绝已存在的目标数据库或异常 sidecar。
2. 严格解析旧 JSON，拒绝未知字段、尾随文档和无效资源引用。
3. 规范化缺省/重复授权，完整保留用户/站点/应用 ID、名称、密码散列、令牌散列、源地址和权限语义。
4. 建立 SQLite schema，将数据作为一次事务写入并发布。
5. 输出资源数量和版本，不输出凭据；原 `state.json` 字节不变。

不自动修改 Server 配置。操作者成功迁移后显式设置 `storage: sqlite`。命令重跑会因目标已存在而失败，不重复导入。要回到 JSON，可导出当前状态，再恢复到一个新的 JSON 数据目录，而不是启动迁移时留下的旧文件。

## 7. 可移植备份

导出格式固定为：`format=tunnel-state`、`version=1`、UTC 导出时间、规范 JSON 状态的 SHA-256，以及完整 State。无论来源后端为何，都可恢复成 JSON 或 SQLite。

校验和用于发现意外修改，不是签名或来源认证。备份含密码/Agent 令牌散列和内部服务地址，不加密；操作者应按敏感数据保存。审计日志、配置文件、环境变量中的明文凭据、TLS/CA 和内存会话不包含在此文件中。

读取与输出 JSON 快照上限 64 MiB。恢复先完成格式、版本、校验和及引用校验，再创建目标目录；失败输入不会触及目的目录。只允许恢复到没有状态文件/SQLite sidecar 的新目录，不覆盖现有部署。

`inspect`、`export`、`migrate`、`restore` 都需要停止 Server；`validate --input` 只验证独立备份，不打开活动数据目录。旧原始 `state.json` 应通过 migrate 处理，不伪装成带版本的 backup。

## 8. 验证与后续

存储合约测试同时覆盖 JSON/SQLite：快照隔离、回调失败、校验失败、提交失败、并发更新、关闭重开、权限和凭据保留。SQLite 测试用真实 SQL trigger 注入事务中途失败，验证磁盘和内存均回滚。子进程测试验证目录锁；备份矩阵覆盖两后端之间四种恢复组合及损坏/未知版本/校验和/悬空授权/sidecar 拒绝。

控制面真实隧道测试和浏览器流程在两个后端运行，发布流程也运行双后端验收。六个平台执行无 CGO 编译。未来 OIDC、共享数据库、会话共享及跨实例隧道路由仍见 [路线图](../roadmap.md)。
