# 组织、角色与隔离边界

第七层依赖多管理员批次。组织拥有成员、站点、应用、用户组、邀请与管理角色；一个普通账号属于一个组织，用户名和 OIDC issuer/sub 仍全局唯一。全局 admin 是平台运维身份，跨组织管理；组织角色不改变持久化 admin/viewer 标记。

## 兼容性与所有权

旧资源属于永久的“默认组织”。持久化以省略/空 organizationID 表示默认组织，API 组织列表用保留 ID `default`；新命名组织使用随机 ID。这样旧 JSON/backup 的省略字段与规范 checksum 保持兼容，升级不改变旧授权。`default` 不能创建、重命名或删除。

创建站点、成员、组、邀请时，全局管理员指定组织，组织操作者默认当前组织且不能指定其他组织。应用从所属站点继承组织。组织和资源归属创建后不可修改；跨组织迁移需要重新创建并重新授权。删除组织要求成员、站点、组、邀请和角色全部为空，避免隐式批量删除。

业务状态验证在每次写入、读取、迁移、restore 时检查组织存在、同组织角色引用，以及用户直接授权、组成员/资源和邀请引用的同组织约束。服务端查询/编辑/删除/轮换/探测/网关也逐条检查，不能只靠 UI 过滤。Agent 的 siteID 和令牌仍是全局唯一站点凭据，不能选择另一个组织的隧道。

## 能力与委派

| 能力 | 组织内范围 |
| --- | --- |
| `sites:manage` | 创建/编辑/删除站点、轮换令牌，影响该站点全部应用和 Agent |
| `applications:manage` | 登记/编辑/删除应用、手动诊断与查看健康状态；自身不授予应用代理访问 |
| `members:manage` | 普通成员生命周期、凭据和直接应用授权 |
| `groups:manage` | 用户组、成员归组和一次性邀请，授予应用访问 |
| `audit:read` | 已标注组织归属的审计记录 |
| `applications:access` | 访问本组织内全部当前/未来应用 |

全局管理员创建、修改、删除角色并将一个角色分配给成员。角色定义只能包含表中能力；没有通配符或 global:admin 能力。组织操作者不能定义/分配管理角色、创建全局管理员或提升自己。持有任何组织角色的账号，其管理修改（密码重置、身份绑定、禁用、删除、直接授权）仅允许全局管理员，避免低能力成员管理员重置更高能力角色账号后接管。角色持有者仍可验证自己的原密码后自助改密。

成员/组管理能力包含委派本组织应用访问的权力；不是仅可分配操作者已经拥有的应用。拥有站点令牌/应用目标配置管理能力的人同样应按站点运维人员信任。Agent 本地 ACL 始终独立生效。组织角色不替代应用自身的账号和权限。

直接/组应用授权仍取并集，再与角色 applications:access 合并；非全局用户首先必须匹配应用组织。管理目录允许本组织的成员/组管理员选择待授权资源；返回 accessible 标记，控制台禁用无访问权的打开按钮，网关独立拒绝。应用管理员可诊断自己的应用，但 launch 仍要求访问权。

角色分配、修改、删除均撤销全部受影响账号的设备会话、票据和 HTTP/WS/SSE。角色删除清除成员 roleID，保留普通账号及其直接/组应用授权，不能遗留旧管理能力。修改角色不会让旧设备静默获得权限。所有管理写入仍在统一访问写锁内鉴权和提交。

## 可见性与审计

全局管理员通过控制台“组织范围”选择资源；组织操作者只看到自己的组织和能力对应入口。成员/资源/API 列表由服务端过滤。组管理员使用最小 `GET /api/group-members` 目录，只返回同组织的成员 ID/用户名/归属，不能借此读取凭据、身份绑定或全部成员管理接口。

全局会话清单、Prometheus 全局指标、管理员管理、组织和角色写入仅全局 admin 可用。成员仍能查看/撤销自己的设备。监控 API 只返回可访问或可管理应用的结果。审计新增 organizationID，系统尽可能从资源归属识别；删除事件显式保留删除前归属。旧记录、无法确定归属和全局管理员操作保留全局可见，不能把缺少字段当默认组织而泄漏历史记录。

## API 与持久化

- `GET /api/organizations`：当前可见组织；全局管理员 POST、PATCH/DELETE `/{id}`。
- `GET /api/roles`：当前组织角色与允许能力；全局管理员 POST、PATCH/DELETE `/{id}`。
- `PATCH /api/users/{id}/role`：全局管理员设置 roleID，空值清除。
- 原有站点/应用/成员/用户组/邀请管理入口复用能力和所有权校验；原字段与默认组织行为兼容。

SQLite schema v4 新增 organization_id/role_id 列，以及 organizations/roles 的有序 JSON payload 表。所有权/角色与 JSON 内引用由域校验约束；不宣称 JSON payload 内引用有 SQL FK。v1/v2/v3 升级均在单事务完成新增、读取与验证，失败回滚。backup v4 读取 v1–v4；restore 仍使未使用邀请失效。当前仍为单实例，不提供共享数据库/会话 HA。

## 验证范围

双后端域校验、v3 实际旧布局升级/失败回滚、跨后端备份恢复；真实 Agent 的跨组织查询/写入/launch/probe/授权/角色/邀请拒绝；管理与访问分离；角色修改后的旧设备/应用拒绝和 WS/SSE 主动关闭。浏览器覆盖组织/角色创建分配、组织操作者可见性、实际应用访问、普通成员创建、角色缩权与删除、手机布局；完整回归保留真实 Keycloak OTP/注销和前六层流程。

尚不支持一个账号同时属于多个组织、组织级 IdP 配置、单组织独立数据库或全局指标分租户导出；不能据此声称完成生产安全审计。
