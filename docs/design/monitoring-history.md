# 业务健康、持久化历史与运维归档

第九层依赖资源/路径目标。监控历史与审计具有独立于授权状态的生命周期，不把会话、隧道或监控数据伪装成共享控制面 HA。

## 健康检查配置

应用新增 healthPath、healthMethod、healthExpectedStatus。默认仍对应用入口执行 HEAD，将 200–399 视为健康；可以选择 GET、相对于挂载前缀的路径，以及 200–599 中一个精确预期状态。状态 0 保持默认范围。路径使用普通相对段，拒绝前导/尾斜杠、query、转义与点段，不能跳出登记的应用路径。

检查通过同一个站点隧道、DNS/ACL/TLS 路径，不跟随重定向，不带用户 Cookie 或应用登录凭据。HTTP 可达与健康分开记录，例如预期 204 而收到 503 为可达但不健康。保持 14 秒超时和四个周期工作者。

应用授权成员及 applications:manage 操作者可手动检查/读取历史。单纯拥有成员/组管理目录不等于有权读健康历史。每条 GET `/api/services/{id}/history` 都重新检查当前应用和组织权限，不用历史中的旧授权决定可见性。

修改健康设置清除当前探测缓存，下一次检查产生新配置结果，不撤销正常应用连接或浏览器会话；URL、站点、域名变更仍沿用完整应用撤销。并发旧配置检查不能覆盖新配置。历史 profile 由站点、目标 URL、检查路径/方法/预期状态构成，名称/访问域名不改变检查历史；默认空方法与显式 HEAD 等价。

## 存储与图表

所有授权状态后端均使用独立 `monitor.db` 保存历史，SQLite application ID `TMON`、schema v1，纯 Go 驱动、FULL 同步和单连接；与 state.db 分开，不改变 JSON 默认选择。Server 启动检查数据库标识、schema、quick_check 和列结构，无法读取的已有库不会重建覆盖。

每条样本只保留检查时间、可达/健康、HTTP 状态、延迟、请求 ID、错误码/阶段，不重复存储完整 DNS/IP 诊断。当前配置最新结果可在重启后恢复，历史诊断详情需重新探测。UTC 固定纳秒格式保证 SQL 字符串排序正确，避免 RFC3339Nano 可变长度导致整秒/小数秒顺序错误。

写入时清理七天以前样本；每应用最多 1,440 条、全局最多 100,000 条。实际覆盖时间还受采集间隔和手动检查影响，图表不承诺完整七天。SQLite 文件可能保留可复用空闲页，限制的是逻辑样本数量。当前配置 API 默认只显示该 profile，旧 profile 按相同保留期清理。

浏览器提供 1 小时/24 小时/7 天窗口、延迟折线、健康条带与最近明细；健康比例按检查次数计算，不是时间加权 SLA。切换应用时忽略过期异步响应。当前状态仍在内存供快速读取；历史写失败不会丢弃本次诊断，记录日志并增加 `tunnel_monitor_storage_errors_total`，运维应告警。

API 支持 `since`（过去的 RFC3339 时间）和 `limit`（1–1440），均有服务端边界。已删除应用和无权应用统一 404，历史不能用于枚举其他组织资源。

## 离线运维归档

普通 `storage export/restore` 只处理授权状态。新增：

| 命令 | 行为 |
| --- | --- |
| `storage export-operations --output ...` | 停机目录锁内归档 audit.jsonl、保留的 .1–.20 和 monitor.db |
| `storage validate-operations --input ...` | 验证条目、SHA-256/大小、完整 gzip footer 和监控数据库 integrity |
| `storage restore-operations --input ...` | 恢复到无运维文件的目录，不覆盖，支持同归档中断恢复 |

格式 `tunnel-operations` v1，manifest 包含文件名、大小、SHA-256、创建时间；仅接收白名单普通文件，拒绝链接、路径穿越、重复条目、未知条目和超过 2 GiB 的解压数据。导出先完整验证再无覆盖发布，私有权限 0600，不包含 state.json/state.db、配置、密码、会话、隧道或密钥环境变量。日志本身仍可能含内部资源与成员信息。

存量 monitor.db 有 journal/WAL/SHM 边车时拒绝直接归档，先正常启动恢复再停机。恢复先验证全包，持有目录锁后写 `operations.restore.pending`，逐文件私有写入/同步/无覆盖发布；最后移除标记。中断后只允许同 manifest 继续，已存在文件必须逐一匹配 checksum。不同内容不覆盖，保留标记供排查。Server 在持有目录锁后再次检查 pending，防止检查与上锁之间的并发窗口。授权状态和运维数据应来自同一停机备份，以匹配资源 ID。

该标记提供崩溃可恢复流程，不声称文件系统支持多文件原子提交。旧版程序不识别标记，恢复期间不可启动旧程序。归档不能恢复进程内会话，Server 重新启动仍需登录。

当前审计 UI 仍查询当前文件末尾；全部保留轮转文件的索引另成下一批，归档工具已包含这些历史文件，不把归档等同于已完成在线索引。

## 验证

双后端健康配置/迁移、真实 Agent 的自定义 GET/204 与 503、健康编辑不撤销应用 Cookie、历史重开持久性/时间排序/保留期/每应用和全局上限/存储故障指标；跨授权与跨组织拒绝。归档覆盖无覆盖、gzip 截断、穿越、符号链接、目录锁、中断续传和 pending 阻止启动。浏览器真实采样/图表/成员边界、停机导出与完整校验、JSON→SQLite 和 SQLite→JSON 配对恢复后再次采样。
