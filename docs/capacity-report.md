# 本地容量验收报告（2026-10-19）

独立 Server + 两个独立 Agent 原生进程，单个合成上游；Linux amd64 / Go 1.27.2 / Node 24.19.0。主机可见 9 个逻辑 CPU，cgroup 配额相当于 8 CPU，主机内存约 9.7 GiB。所有流量走回环，HTTP 明文仅用于回环测试；没有真实 WAN/TLS、生产应用处理或落盘上传。

两轮分别使用 JSON/SQLite 授权状态；请求期间读取的是内存授权状态，两者的审计索引始终使用 SQLite。因此下表不是两种授权数据库写入性能的比较，单次观测差异也不能解释为存储性能优势。

| 工作负载 | 并发 | JSON 请求/秒 | JSON p95 ms | SQLite 请求/秒 | SQLite p95 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| http-4KiB | 1 | 315.2 | 6.08 | 427.0 | 3.21 |
| http-4KiB | 8 | 592.9 | 17.76 | 688.5 | 13.87 |
| http-4KiB | 32 | 554.7 | 124.30 | 705.7 | 51.89 |
| upload-1MiB | 4 | 289.5 | 31.62 | 339.9 | 16.06 |
| http-with-16WS-16SSE | 16 | 576.4 | 32.52 | 664.4 | 29.90 |
| http-one-surviving-Agent | 8 | 719.0 | 13.84 | 710.8 | 15.29 |

HTTP 4 KiB 每档 600 次，混合流量 HTTP 600 次，单 Agent 300 次；上传为 4 并发、32 次各 1 MiB，分别约 289.5 / 339.9 MiB/s（上游只接收计数，不落盘）。两轮共 5,464 次计量 HTTP 请求均无错误。WS/SSE 同时各 16 条，约 3 秒观测期间均无流错误；SSE 报告的是 read chunk，可能合并多个事件。

| 峰值（100ms 采样） | JSON RSS MiB / FD | SQLite RSS MiB / FD |
| --- | ---: | ---: |
| Server | 31.3 / 50 | 32.2 / 53 |
| Agent 1 | 20.6 / 19 | 21.9 / 22 |
| Agent 2 | 20.2 / 19 | 21.4 / 23 |

资源峰值只包含 Server/Agent，不含浏览器、上游和负载生成器，短于采样周期的尖峰可能遗漏。

优雅 SIGTERM 停止一个 Agent 后，在线清单约 3.5 / 3.4 ms 检测其离线，剩余 Agent 的 300 次请求均成功；重启原 Agent 到清单在线约 56.0 / 55.3 ms，包含约 50ms 的轮询量化。这不是网络黑洞、主机断电或 WAN 重连时延测量。

## 解释与边界

- JSON 32 并发相较 8 并发吞吐没有提高、p95 明显上升；当前基线不据此增大每应用连接上限。应先在目标硬件上分析审计/磁盘、调度和真实上游延迟，再调整参数。
- 这次测量没有运行到饱和点，没有持续数小时的资源泄漏检验，也不代表最大生产会话数。生产需补实际 RTT/TLS、连接绑定应用、真实上游 CPU/IO、故障注入和目标 SLO。
- 性能脚本使用共享连接池；会话隔离串行模式通过独立功能/浏览器测试，不能套用这里的共享模式吞吐。
- 原始报告记录了当时父提交和 workingTreeDirty=true；测试二进制来自本 PR 工作区实现，报告与实现一并提交。发布候选仍应对最终提交在目标环境重跑。
